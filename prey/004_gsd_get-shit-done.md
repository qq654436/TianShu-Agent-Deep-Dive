## 📦 项目概述

**GSD (Get Shit Done)** 是一个轻量级但强大的元提示 (meta-prompting)、上下文工程 (context engineering) 和规范驱动开发 (spec-driven development) 系统。

**核心价值主张**:
> "Solves context rot — the quality degradation that happens as Claude fills its context window."

**解决的问题**:
- Vibecoding 的坏名声：描述需求 → AI 生成代码 → 得到不一致的垃圾
- 现有工具过度复杂：BMAD、SpecKit 等引入企业级流程 (sprint ceremonies、story points、Jira workflows)
- 独立开发者不需要扮演 50 人工程团队

**目标用户**: 想要描述需求并正确构建的独立开发者

## 🔄 工作流程

### 阶段 1: 项目初始化

```bash
/gsd:new-project
```

**系统执行**:
1. **问题** - 持续提问直到完全理解想法 (目标、约束、技术偏好、边界情况)
2. **研究** - 生成并行代理调查领域 (可选但推荐)
3. **需求** - 提取 v1、v2 和范围外内容
4. **路线图** - 创建映射到需求的阶段

**产出文件**:
- `PROJECT.md` - 项目愿景和目标
- `REQUIREMENTS.md` - 详细需求列表
- `ROADMAP.md` - 阶段路线图
- `STATE.md` - 项目状态追踪
- `.planning/research/` - 研究报告

---

### 阶段 2: 讨论阶段

```bash
/gsd:discuss-phase 1
```

**这是塑造实现的关键步骤。**

系统分析阶段并识别灰色区域：
- **视觉特性** → 布局、密度、交互、空状态
- **APIs/CLIs** → 响应格式、标志、错误处理、详细程度
- **内容系统** → 结构、语气、深度、流程
- **组织任务** → 分组标准、命名、重复项、例外

**产出文件**: `{phase_num}-CONTEXT.md`

---

### 阶段 3: 规划阶段

```bash
/gsd:plan-phase 1
```

**系统执行**:
1. **研究** - 调查如何实现此阶段，由 CONTEXT.md 决策指导
2. **规划** - 创建 2-3 个原子任务计划 (XML 结构)
3. **验证** - 对照需求检查计划，循环直到通过

**产出文件**:
- `{phase_num}-RESEARCH.md` - 技术调研报告
- `{phase_num}-{N}-PLAN.md` - 原子任务计划

---

### 阶段 4: 执行阶段

```bash
/gsd:execute-phase 1
```

**系统执行**:
1. **波次运行计划** - 可能时并行，依赖时顺序
2. **每个计划新鲜上下文** - 200k tokens 纯用于实现，零累积垃圾
3. **每个任务提交** - 每个任务独立原子提交
4. **对照目标验证** - 检查代码库交付阶段承诺

**波次执行示例**:
```
┌────────────────────────────────────────────────────────────┐
│  PHASE EXECUTION                                           │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  WAVE 1 (parallel)    WAVE 2 (parallel)    WAVE 3          │
│  ┌─────────┐ ┌─────┐  ┌─────────┐ ┌─────┐  ┌─────────┐    │
│  │ Plan 01 │ │ 02  │→ │ Plan 03 │ │ 04  │→ │ Plan 05 │    │
│  │ User    │ │Prod │  │ Orders  │ │Cart │  │Checkout │    │
│  │ Model   │ │Model│  │ API     │ │ API │  │ UI      │    │
```

## 🔍 技术深度分析

### 1. 上下文工程 (Context Engineering)

**问题**: AI 编程中，随着对话进行，上下文窗口被填充，导致：
- 早期重要信息被遗忘
- AI 开始"我会更简洁"的降级行为
- 代码质量下降

**GSD 解决方案**:
```
┌─────────────────────────────────────────────────────────┐
│  CONTEXT MANAGEMENT                                     │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  传统方式:                                              │
│  [对话历史 1] + [对话历史 2] + ... + [当前任务]        │
│  → 上下文窗口填满 → 质量下降                           │
│                                                         │
│  GSD 方式:                                              │
│  [CONTEXT.md] + [STATE.md] + [当前任务]                │
│  → 只加载相关上下文 → 质量稳定                         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**实现要点**:
- 所有决策外部化为 Markdown 文件
- 每个任务只加载必要的上下文
- 使用 XML 标签结构化关键信息

---

### 2. 元提示系统 (Meta-Prompting)

**定义**: 提示的提示 - 定义如何生成和使用提示的系统

**GSD 的元提示层次**:
```
Level 1: 系统提示 (System Prompt)
  └─ 定义 AI 角色和行为准则

Level 2: 任务提示 (Task Prompt)
  └─ 定义具体任务目标和约束

Level 3: 上下文提示 (Context Prompt)
  └─ 从 CONTEXT.md/STATE.md 动态注入

Level 4: 验证提示 (Validation Prompt)
  └─ 检查输出是否符合要求
```

**天枢可借鉴**:
- 在 `sessions_spawn` 时注入结构化上下文
- 为子代理定义清晰的验证提示

---

### 3. 子代理编排 (Subagent Orchestration)

**GSD 的代理类型**:
| 代理 | 职责 | 并行度 |
|------|------|--------|
| 问题代理 | 澄清用户需求 | 1 |
| 研究代理 | 调查技术方案 | N (并行) |
| 规划代理 | 创建执行计划 | 1 |
| 执行代理 | 实现具体任务 | N (波次并行) |
| 验证代理 | 检查输出质量 | 1 |

**天枢对比**:
- 天枢使用 `sessions_spawn` 生成子代理
- GSD 使用内部代理系统 (硬编码)
- **天枢优势**: 更灵活，可动态生成任意类型代理
- **GSD 优势**: 更轻量，启动更快
