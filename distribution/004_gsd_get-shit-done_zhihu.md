## 前言

在 AI 辅助编程领域，有一个普遍存在但鲜被讨论的问题：**上下文腐烂 (Context Rot)**。

简单来说，就是随着对话进行，AI 的上下文窗口逐渐被填充，导致早期的重要信息被遗忘，代码质量随之下滑。

你可能见过这种场景：

> 刚开始让 AI 写代码，输出质量很高。
> 
> 对话进行到第 10 轮，AI 开始说"为了简洁，我会..."
> 
> 第 20 轮，代码开始出现低级错误，架构一致性丧失。

这不是 AI 变笨了，而是**上下文窗口管理**的问题。

今天要拆解的开源项目 **GSD (Get Shit Done)**，提供了一个优雅的解决方案。

## 技术架构深度分析

### 1. 上下文工程 (Context Engineering)

GSD 定义了两个核心文件：

**CONTEXT.md** - 用户偏好捕获
- 视觉特性：布局、密度、交互、空状态
- API/CLI：响应格式、错误处理、详细程度
- 内容系统：结构、语气、深度、流程
- 组织任务：分组标准、命名、重复项、例外

**STATE.md** - 项目状态追踪
- 当前阶段
- 已完成任务
- 待办事项
- 关键决策历史

这两个文件构成了项目的"外部记忆"，AI 每次执行任务时只加载必要的上下文。

### 2. 元提示系统 (Meta-Prompting)

GSD 使用四层提示结构：

```
Level 1: 系统提示 (System Prompt)
  └─ 定义 AI 角色和行为准则

Level 2: 任务提示 (Task Prompt)
  └─ 定义具体任务目标和约束

Level 3: 上下文提示 (Context Prompt)
  └─ 从 CONTEXT.md/STATE.md 动态注入

Level 4: 验证提示 (Validation Prompt)
  └─ 检查输出是否符合要求
```

这种分层结构确保了：
- AI 清楚自己的角色
- 任务目标明确
- 上下文相关且精简
- 输出可验证

### 3. 子代理编排 (Subagent Orchestration)

GSD 定义了五种代理类型：

| 代理 | 职责 | 并行度 |
|------|------|--------|
| 问题代理 | 澄清用户需求 | 1 |
| 研究代理 | 调查技术方案 | N (并行) |
| 规划代理 | 创建执行计划 | 1 |
| 执行代理 | 实现具体任务 | N (波次并行) |
| 验证代理 | 检查输出质量 | 1 |

**关键创新**: **波次执行 (Wave Execution)**

系统分析任务依赖关系，将任务分组为"波次"：
- 同波次内的任务 → 并行执行
- 波次之间 → 顺序执行

```
WAVE 1 (并行)        WAVE 2 (并行)        WAVE 3 (串行)
┌─────────┐ ┌─────┐  ┌─────────┐ ┌─────┐  ┌─────────┐
│ Plan 01 │ │ 02  │→ │ Plan 03 │ │ 04  │→ │ Plan 05 │
│ User    │ │Prod │  │ Orders  │ │Cart │  │Checkout │
│ Model   │ │Model│  │ API     │ │ API │  │ UI      │
└─────────┘ └─────┘  └─────────┘ └─────┘  └─────────┘
```

### 4. XML 提示格式化

GSD 使用 XML 标签结构化关键信息：

```xml
<task>
  <goal>实现用户认证模块</goal>
  <constraints>
    <constraint>使用 JWT token</constraint>
    <constraint>支持 refresh token 轮换</constraint>
  </constraints>
  <context>
    <file src="CONTEXT.md" section="api-style"/>
    <file src="STATE.md" section="completed-tasks"/>
  </context>
  <output>
    <format>TypeScript + Express</format>
    <tests>required</tests>
  </output>
</task>
```

这种格式化的好处：
- AI 输出结构一致
- 便于程序解析和验证
- 减少歧义

## 工作流程详解

### 阶段 1: 项目初始化

```bash
/gsd:new-project
```

**系统执行**:
1. **问题** - 持续提问直到完全理解想法
2. **研究** - 生成并行代理调查领域
3. **需求** - 提取 v1、v2 和范围外内容
4. **路线图** - 创建映射到需求的阶段

**产出**:
- `PROJECT.md` - 项目愿景
- `REQUIREMENTS.md` - 详细需求
- `ROADMAP.md` - 阶段路线图
- `STATE.md` - 状态追踪

### 阶段 2: 讨论阶段

```bash
/gsd:discuss-phase 1
```

**这是塑造实现的关键步骤。**

系统分析阶段类型，识别灰色区域：
- 视觉特性 → 布局、密度、交互
- API/CLI → 响应格式、错误处理
- 内容系统 → 结构、语气
- 组织任务 → 分组、命名

输出 `CONTEXT.md`，直接指导后续研究和规划。

### 阶段 3: 规划阶段

```bash
/gsd:plan-phase 1
```

**系统执行**:
1. **研究** - 调查实现方案，由 CONTEXT.md 指导
2. **规划** - 创建 2-3 个原子任务计划 (XML 结构)
3. **验证** - 对照需求检查计划，循环直到通过

**产出**:
- `N-RESEARCH.md` - 技术调研
- `N-1-PLAN.md` - 任务计划 1
- `N-2-PLAN.md` - 任务计划 2

### 阶段 4: 执行阶段

```bash
/gsd:execute-phase 1
```

**系统执行**:
1. **波次运行** - 依赖感知的并行调度
2. **新鲜上下文** - 每个计划 200k tokens 可用
3. **原子提交** - 每个任务独立 git commit
4. **验证** - 对照目标检查代码质量

## 与天枢计划的对比

作为天枢计划的持续拆解者，我发现 GSD 与天枢有很多相似理念：

| 维度 | GSD | 天枢计划 |
|------|-----|----------|
| **状态管理** | CONTEXT.md + STATE.md | memory/ + LONG_TERM_MEMORY.md |
| **周期性任务** | 无 (按需触发) | HEARTBEAT.md 定义 |
| **子代理** | 硬编码 5 种代理 | sessions_spawn 动态生成 |
| **验证机制** | 计划验证 + 执行验证 | 执行前/后/会话结束三层验证 |
| **目标定位** | AI 编程工具链 | 一人公司操作系统 |

**GSD 的优势**:
- 更轻量，启动更快
- 专注于代码实现
- 支持多种 AI 运行时

**天枢的优势**:
- 更通用，可扩展
- 涵盖业务运营
- 长期记忆系统

**可借鉴点**:
1. XML 提示格式化 → 提高子代理输出质量
2. 波次执行 → 优化并行任务调度
3. CONTEXT.md 模式 → 增强用户偏好捕获
